# Contributing Guide

> **Version** 0.1.0 · **Updated** 2026-06-08 · **Language** English · [简体中文](CONTRIBUTING.md)

Thank you for your interest in ZestFlow. This document explains how to contribute code and documentation.

---

## Code of conduct

- Respect discussion; critique ideas, not people
- Provide reproducible steps or minimal examples in Issues
- Keep PRs focused on a single topic; avoid unrelated changes

---

## Development environment

1. Fork the repository (Gitee / GitHub)
2. JDK 17+, Maven 3.8+, MySQL 8+
3. Start Admin + Demo per [docs/GETTING_STARTED.en.md](docs/GETTING_STARTED.en.md)

```bash
git clone <your-fork>
cd zestflow
mvn install -pl zestflow-demo -am -DskipTests
```

---

## Pre-commit checks

```bash
# Core module unit tests
mvn test -pl zestflow-admin,zestflow-executor,zestflow-common -am

# Demo integration tests (optional, slower)
mvn test -pl zestflow-demo -am

# Frontend (if admin-ui changed)
cd zestflow-admin-ui && pnpm test:unit && pnpm build
```

## Code standards

Project conventions are in [CLAUDE.md](CLAUDE.md). Key points:

| Area | Requirement |
|------|-------------|
| Package naming | `com.zestflow.{module}.{layer}` |
| Layering | Controller → Service → Repository; no cross-layer calls |
| Module dependencies | Each tier depends only on `zestflow-common`; no Admin ↔ Executor direct dependency |
| Database changes | Flyway `db/migration/V{n}__*.sql` only; no Java DDL |
| Frontend UI text | Must use i18n; no hardcoded Chinese/English |
| Code generation | Design/chain codes auto-generated by `CodeGenerator`; no manual entry |

## Documentation contributions

1. Read [docs/DOCUMENTATION_MAINTENANCE.en.md](docs/DOCUMENTATION_MAINTENANCE.en.md)
2. Choose document type per [Diátaxis](https://diataxis.fr/) (Tutorial / How-to / Explanation / Reference)
3. Update document header **Version** and **Updated** date
4. Configuration changes must sync [docs/reference/CONFIGURATION.md](docs/reference/CONFIGURATION.en.md)
5. When adding English docs, mirror structure in `*.en.md` and link both ways

---

## Pull request process

1. Create a feature branch from `main`: `feat/xxx` or `fix/xxx`
2. Commit message: briefly explain **why** (Chinese or English)
3. Ensure CI passes
4. PR description: change summary + how you tested
5. Wait for review
